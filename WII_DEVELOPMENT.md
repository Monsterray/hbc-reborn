# Wii homebrew return path and development setup

Research note for the HBC installed-title return test, based on current project code, upstream source, and the 2026-09-27 debugger run.

## What the HBC return path does

The libogc contract has two distinct exit behaviors. Its `SYS_RETURNTOMENU` reset type loads the Wii Channels menu directly. Separately, libogc checks for the HBC reload stub at `0x80001800` when `exit()` runs. If it finds the `STUBHAXX` marker at `0x80001804`, libogc shuts down services with `SYS_SHUTDOWN` and branches to the stub. If no stub is present, it uses `SYS_HOTRESET` on Wii. The `SYS_MainLoop()` documentation explicitly warns that when it returns false, returning from `main()` or calling `exit()` bypasses the reload stub and lets libogc reset or power off. See [libogc `system.c`](https://github.com/devkitPro/libogc/blob/master/libogc/system.c#L2498-L2596) and [libogc `system.h`](https://github.com/devkitPro/libogc/blob/master/gc/ogc/system.h#L1164-L1182) / [SYS_MainLoop documentation](https://github.com/devkitPro/libogc/blob/master/gc/ogc/system.h#L1502-L1539).

The HBC stub is a reloadable title launcher, not a C return to the old process. It starts at `0x80001800`, reads an optional magic/title pair at `0x80002f00` and `0x80002f08`, cleans up IPC state, opens `/dev/es`, gets the destination title's ticket views, and submits ES ioctl `0x08` through the rebooting IOS IPC handshake. The current HBC source and this checkout implement that path in [`stub.c`](channel/channelapp/stub/stub.c), [`ios.c`](channel/channelapp/stub/ios.c), and [`main.c`](channel/channelapp/source/main.c). The HBC startup copies the stub to `0x80001800`, flushes it, and stores the active title ID plus a magic value; when HBC detects an already installed `STUBHAXX` stub from the launching channel, it preserves it. Upstream source: [HBC `main.c`](https://github.com/fail0verflow/hbc/blob/master/channel/channelapp/source/main.c), [HBC `stub.c`](https://github.com/fail0verflow/hbc/blob/master/channel/channelapp/stub/stub.c), [HBC `ios.c`](https://github.com/fail0verflow/hbc/blob/master/channel/channelapp/stub/ios.c).

As a reference implementation, current libogc's `WII_LaunchTitle` also obtains ticket views, writes the Wii NAND boot-info record (including the launcher title ID), blacks and flushes video, and calls `ES_LaunchTitle`; it returns an error if the call unexpectedly returns. That gives us a concrete comparison when checking a direct ES ioctl implementation, while not proving the HBC stub must duplicate every wrapper step. Source: [libogc `wiilaunch.c`](https://github.com/devkitPro/libogc/blob/master/libogc/wiilaunch.c#L1390-L1462).

The addresses and marker are shared conventions, not evidence that the stub ran. Dolphin's HLE fixed-function patcher normally installs an `HBReload` hook at `0x80001800` and writes `STUBHAXX` at `0x80001804` when cheats are disabled. Its hook stops emulation, which appeared here as Dolphin's “Confirm stopping emulation” dialog. Thus a normal Dolphin homebrew launch can satisfy libogc's stub check while entering Dolphin's HLE return hook instead of HBC's actual code. The Dolphin source says the patch is skipped when cheats are enabled; for a meaningful real-stub test, use a disposable profile, enable cheats with no Gecko codes, and confirm the debugger's PC reaches `0x80001800`. Run the default HLE path as a separate compatibility case. Source: [Dolphin `HLE.cpp`, `PatchFixedFunctions`](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/HLE/HLE.cpp), [Dolphin `HLE_Misc.cpp`, `HBReload`](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/HLE/HLE_Misc.cpp), and [Dolphin core settings](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/Config/MainSettings.cpp).

For installed-title return, the expected result is that ES launches the title ID remembered by HBC, so IOS reload/title-launch must complete and the HBC channel must be re-entered as a NAND title. HBC's upstream README cautions that direct DOL launch does not have the installed channel's NAND identity and that NAND save/theme behavior therefore differs; compare DOL and installed WAD runs as separate tests. See [HBC README](https://github.com/fail0verflow/hbc#the-homebrew-channel). HBC 1.1.x release notes also call out reload-stub support for arbitrary BAT layouts and real mode, independent of existing exception vectors, disabling IRQs early, and avoiding HID4 writes. See the [HBC source/release history](https://wiibrew.org/wiki/Homebrew_Channel#Changelog) and the implementation in [`crt0.S`](channel/channelapp/stub/crt0.S).

### Reading the current black-screen result

With Dolphin's HLE hook bypassed, the debugger confirmed the installed WAD's 4992-byte stub was present at `0x80001800` with `STUBHAXX`, `LOADKTHX`, and title `000100014f484243`. The exit-test app entered `_main`, opened `/dev/es`, then attempted to reload the already active IOS58. It hung while waiting for an IPC ACK during the second `/dev/es` open. The focused fix skips the reload and second open when the requested IOS is already active; the installed-title return still needs a run against that build. The stub emits serial/USB Gecko debug messages for these stages (`Opening /dev/es`, ticket-view queries, and `Attempting to launch`). See [`stub.c`](channel/channelapp/stub/stub.c) and [`ios.c`](channel/channelapp/stub/ios.c).

For a controlled comparison, keep the same WAD and NAND profile and vary one thing at a time: (1) ordinary Dolphin HLE hook with cheats disabled; (2) actual stub with cheats enabled and no codes; (3) actual stub with the debugger detached. Confirm whether the screen is black while the debugger is paused; resume execution before interpreting the result. Inspect Dolphin's log and the guest PC, and record the exact IOS version, HBC title ID, and return title ID. A black screen seen while execution is paused is not evidence that the unpaused transition is stuck.

## Development setup and habits

For a new Wii project, devkitPro's current setup instructions install the `wii-dev` package group through devkitPro pacman; this supplies devkitPPC and the Wii libraries. Use its [devkitPPC getting-started guide](https://devkitpro.org/wiki/Getting_Started/devkitPPC), the maintained [Wii examples](https://github.com/devkitPro/wii-examples), and the installed `wii_rules` rather than copying an old standalone toolchain recipe. devkitPro's current examples continue to receive updates; the May 2026 release specifically says it updates examples for libogc 3.0 and adds missing `SYS_MainLoop` calls. See [wii-examples releases](https://github.com/devkitPro/wii-examples/releases).

Use the standard Wii compiler target flags/rules from the installed toolchain, keep a reproducible build log and ELF/map file alongside each DOL, and use the ELF from that exact build to resolve debugger PCs. Build the ordinary DOL separately from the installable WAD: the two boot modes have different title/NAND identity and exercise different code. For app-return and NAND behavior, import the WAD into a fresh Dolphin user directory; do not infer installed-title behavior from a direct DOL boot. Dolphin supports a per-user directory via `-u`; see its [global user directory guide](https://dolphin-emu.org/docs/guides/controlling-global-user-directory/). Keep the SD image/profile disposable and preserve the WAD, ELF, map, and emulator log for each run.

The HBC upstream build notes are useful for this older project specifically: they name devkitPPC/libogc/libfat plus zlib, libpng, mxml, and freetype, and host dependencies for PyWii/WAD packaging. They also explicitly distinguish channel WAD from standalone executable behavior. See [HBC build instructions](https://github.com/fail0verflow/hbc#build-instructions). This checkout's project skill supplies the exact local build commands and isolated Dolphin workflow; retain those rather than replacing its custom channel packaging with a generic template.
