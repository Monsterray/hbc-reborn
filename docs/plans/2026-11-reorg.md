# Repository reorganization (November 2026)

A plan to make hbc-reborn easier to find your way around, for people first and
agents second. Each phase lands on `develop` as its own small set of commits,
with CI green before the next one starts.

## Decisions so far

- Tests get folders by kind, an audit for duplicates and speed, and a shared
  library for code the scripts repeat.
- `tools/wii-bench/` leaves hbc-reborn for a repository of its own,
  `C:/projects/wii-bench`, together with wii-homebrew-kit (both histories
  kept). Local only for now; no GitHub remote yet.
- Tools are sorted by use: kept tools stay in `tools/`, one-off research
  scripts go to `tools/research/`. Every kept tool gets a proper `--help`.
- The root keeps only what people open often.
- Every SDK is a folder with its own README.
- The docs get an overhaul, with the GitHub wiki as a second home for guides.
- The Message Board and Mii docs are merged as proposed.
- Git: finished branches and worktrees are removed; work in progress stays.

## Phase 1: wii-bench into its own repository

The bench is used by about ten projects (WiiStation, Wii64, vbagx, bootmii-reborn,
usbloadergx, usbloadergx-bench, d2x-cios, priiloader-reborn, wii-homebrew-kit,
and the `wii-homebrew` skill), most through the absolute path
`C:/projects/hbc-reborn/tools/wii-bench/wiibench.py`. Its queue state lives in
`C:/tools/wii-bench` (`$WII_BENCH_HOME`), not in the checkout, so moving the code
does not disturb a running queue.

Steps:

1. Done 2026-11-07: `C:/projects/wii-bench` holds `tools/wii-bench` (now
   `bench/`) and `tests/test_wiibench.py` with their history, merged with
   wii-homebrew-kit's history.
2. Done: the bench finds HBC's client through `$HBC_PY`, with
   `../hbc-reborn/tools/hbc.py` as the default; its tests take the fake HBC
   from the same checkout. All 95 queue tests pass there.
3. Cut over: `python C:/projects/wii-bench/bench/wiibench.py setup` points
   the shim at `C:/tools/wii-bench/wiibench.py` to the new copy (only with no
   job running).
4. Leave forwarding stubs at `tools/wii-bench/wiibench.py` and `monitor.sh` in
   hbc-reborn that run the new copy and print where it moved. Remove them once
   every project points at the new path.
5. Update the other projects' references, one commit each.
6. Move the lease server's compose deployment on the home server to the new
   checkout.

### The kit and the bench together?

Recommended: **yes, one repository.** The kit already documents the bench
(`docs/bench.md`), ships the guards the bench enforces (`tools/wii_targets.py`)
and the Dolphin runner, and every project that adopts the kit also uses the
queue. The kit has 12 commits and no remote, so merging it costs little. Layout:

```
<new repo>/
  bench/        wiibench.py, monitor.sh, lease server (Dockerfile, compose.yaml)
  template/     the files the kit copies into a project
  tools/        adopt.py, wii_targets.py, dolphin_run.py
  docs/         bench, Dolphin, capture card, testing layers, adopting
  tests/
```

## Phase 2: tests

1. **Folders by kind**, with names that say where a test runs:

   | Folder | Runs on | Now |
   | --- | --- | --- |
   | `tests/host/` | This PC, no Wii | `test_*.py`, `*_host/` |
   | `tests/dolphin/` | Dolphin | `dolphin_*.py` |
   | `tests/wii/` | The bench Wii, through the queue | `wii_*.py` |
   | `tests/apps/` | Test DOLs the above send | `*_app/`, `netblock/`, `membench/`, ... |
   | `tests/lib/` | Shared Python helpers | new |

2. **`tests/lib/`** replaces the 64 `sys.path` inserts and the repeated helpers
   (launching an app, waiting for HBC, pictures, snapshots, the bench guard).
   One `conftest.py` or `__init__.py` sets the path once.
3. **Audit**, written down per test: what it proves, how long it takes, which
   other test covers the same thing. Merge tests that prove the same thing;
   share one Dolphin boot across tests where the state allows it; never drop a
   check without naming the test that still makes it.
4. **One way to run each layer**, in the README test table and CI.
5. **A searchable index**: `tests/README.md`, one line per test with its layer,
   runtime and what it covers.

## Phase 5: SDKs

Every SDK becomes `sdk/<name>/` with the same shape:

```
sdk/<name>/
  README.md     what it does, a screenshot or diagram, a 10-line example,
                the API at a glance, limits, version history
  <name>.h, <name>.c
  example/      a small app that builds
```

`sdk/hbc_agent.h` and `sdk/hbc_netlog.h` move into `sdk/hbc_agent/` and
`sdk/hbc_netlog/`. A one-release forwarding header at the old path keeps
existing apps building. `sdk/README.md` becomes the catalog: one card per SDK.

README style: modern structure (badges, a short pitch, a table of contents,
copy-paste examples), classic feel (plain prose, monospace API tables, the
Wii-era look in the screenshots). People first: what it does and a working
example before details. Agents second: exact function names, error codes and
limits in tables they can search.

## Phase 6: docs

1. **Split REVIEW.md**: per-release results to `CHANGELOG.md` (short) and
   `docs/history/` (the evidence); the plan and open findings stay in
   `docs/review.md`.
2. **Trim README.md** to: what HBC reborn is, install, quick start, links.
   SDK tutorials move to each SDK's README; `hbc.py` reference to
   `docs/hbc-py.md`; building and testing to `CONTRIBUTING.md`.
3. **Message Board**: `docs/mboard/` with `README.md` (the guide, from
   `docs/mboard.md`), `storage.md` (from `messageboard-messages.md`) and
   `play-log.md` (from `messageboard.md`, its "untested" note checked and
   updated). Mii the same way: `docs/mii/` with the guide, the data format,
   and `research/`. `mii-sdk-2.md` moves to `docs/plans/`.
4. **`docs/README.md`**: an index of every doc, grouped by reader (app
   developer, contributor, researcher).
5. **GitHub wiki**: guides for app developers (install, `hbc.py`, each SDK's
   tutorial, FAQ) published from `docs/` by a script, so the repository stays
   the source and the wiki never drifts. Research and contributor docs stay in
   the repository only.

## Order

Phase 0, then 1 (the user asked to start there), then 4 and 6.1 (root and
REVIEW split), 5, 6.2-6.5, 2 and 3. Tests and tools go last because their
paths are referenced by the most docs; moving docs first means those links are
fixed once.
