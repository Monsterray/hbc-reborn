# HBC 1.15.x: findings and hardware results

What each 1.15.x change found, fixed and measured, newest first. The short list of
changes is in [CHANGELOG.md](../../CHANGELOG.md); open items are in
[review.md](../review.md).

## 1.15.21: a pulled drive leaves status; a file that is not a DOL is refused

From the replug-tests branch (written on 1.15.15, ported to the new test
layout):

- `app_entry_scan` watches the app list's device each second. A drive that
  only a file request had mounted, or had found unmountable, kept showing as
  "inserted" (or "unmountable") after it was pulled, until the next request
  to that drive. The scan now drops both, and clears the status of a lost app
  list device. `extra_lock` is made by `app_entry_init` instead of by the
  first file request, so the scan never tests a lock another thread may be
  creating. `_mount` and the shut-down take it too.
- `loader_reloc.c`: a DOL's entry point must lie in one of its sections. A
  file of zeros (the replug test's dummy app) had none and entry point 0;
  starting it read address 0x20 and crashed HBC. A truncated or corrupt
  `boot.dol` now fails to load with an error, as a bad ELF did.
- Tests: `tests/dolphin/dolphin_replug.py` toggles Dolphin's SD card while HBC
  runs. Its out, in, three quick cycles and 15 s out all recover, and file
  requests and the list come back. `tests/wii/wii_replug.py` is the attended
  SD and USB version; it has not run on a Wii yet.
- Dolphin tests: Wii Remote 1 and GameCube pad 1 are no longer this PC's
  keyboard and mouse. With background input on, a click on the desktop was A
  in HBC, which launched the dummy app mid-test. Hotkeys also need
  `HotkeysRequireFocus=False`, or they work only while Dolphin's window has
  focus.
- The smoke test checks `hbc.py`'s own refusal of `rm -r` with a pattern at a
  device's top apart from the Wii's (since 1.14.16 `hbc.py` refused first, so
  the test failed).
- `tools/check_secrets.py` and the `tools/hooks/pre-push` hook stop a push that
  carries Wii keys, signing keys, console dumps or tokens (see CONTRIBUTING.md).

## 1.15.20: a stuck USB drive no longer holds HBC on a black screen

The problem: d2x's watchdog reset the dev Wii while a USB drive was
mid-transfer (d2x usb-spin). The drive then NAKs for ever, and IOS58's USB
module never answers again. Every IOS request sent after it waits too (ES,
NAND, SD, the network, Bluetooth, IOS_ReloadIOS), so HBC stopped at
gfx_init_video's `is_vwii` (an ES call) with the screen black. Only a pull
or a replug clears the drive; a reset does not. Priiloader is not affected,
because IOS80 has no EHCI driver.

This version was developed as test builds 1.15.17 to 1.15.19, which were
never pushed:

- 1.15.17 timed every blocking IOS call of start-up and the drive scan
  (`bootlog.c`, `hbc.py status` "calls"; a call with "out": null is the
  one IOS never answered). It also drew the list on the TV when the menu
  is not up after 5 s (`bootscreen.c`). On the dev Wii, the USB probes sat
  for 88 minutes, until the drive was pulled, and the NAND, ES, SD and
  network probes behind them waited just as long.
- 1.15.18 asked `/dev/usb/oh1` first. It answered in 2 ms, so HBC stayed on
  IOS58, and WPAD_Init then waited 67 s.
- 1.15.19 asks what WPAD_Init asks, in its order: open `/dev/usb/ven`, its
  version, then the Bluetooth device. The 1.15.17 probes showed ven and hid
  hang.

What 1.15.20 does (`usbstart.c`, on [sdk/usbguard](../../sdk/usbguard/README.md)):

- With no answer in 1.5 s and AHBPROT, HBC clears PE on each EHCI port that
  has a drive (`usbguard_free`). That frees IOS just as a pull does; a
  reload or a port reset does not. HBC then starts with Wii Remotes but no
  USB drives.
- Otherwise it reloads IOS80 (ES patched for AHBPROT first) and starts
  without USB drives and keyboards. If that reload fails too, it starts
  without Wii Remotes, on the GameCube controller.
- Until the drive is pulled, a menu launch warns first and a network launch
  is refused with the `usb_stuck` message, since an app that reloads IOS
  would hang on the drive. d2x rc3 gives up after about 7 s with -101; d2x
  rc1, upstream d2x 11.0 and IOS58 hang.
- Status: `usb_stuck`, `usb_unplugged`, `remotes_off`, `replug_needed`, and `ehci` (the
  registers at each unplug step).
- The keyboard's USB set-up runs on a worker thread and stops between steps
  when HBC shuts down. Test builds: `HBC_TEST_USB_STUCK` takes the stuck
  path, `HBC_TEST_BOOT_STALL` stalls start-up 12 s (Dolphin).

Checked on the dev Wii with d2x usb-spin, before the code was split into
`bootlog.c`, `bootscreen.c` and `usbstart.c`:

- HBC freed the stuck drive at start-up, and the menu was up at 1.9 s.
- Network sends were refused with the full `usb_stuck` message, and HBC kept
  answering after each one.
- `tests/wii/wii_usbguard.py` (attended) passed. The test app warned at
  5.0 s, waited for the replug after a pull and mounted, and A freed it
  (FREED).

Not checked on a Wii: the menu launch warning, pull detection from the
menu, and the build after the split (host tests, Dolphin's usbguard check
and a warning-free build only).

  kept answering (1.15.12 DOL, job 20261105-092808-e4bb81).

## 1.15.12: the keyboard's IOS report buffer has a cache line of its own

Fourth audit, item 15 (hardening): in `struct kbd`, `report[8]` and `keys[8]`
shared one 32-byte cache line. `report` is written by IOS, and libogc
invalidates its line when a read ends, so an invalidate could drop a CPU
write to `keys`. `keys` now sits before the buffer, and `report` is a full
32-byte aligned line (the struct stays a multiple of 32), checked with a
`_Static_assert`. keyboard.c has no `DCInvalidate` or `DCFlush` of its own:
`USB_ReadIntrMsgAsync` handles the buffer with the 8-byte length, which
covers just that line. No host test (libogc USB). Checked: build with
`-Werror`.

## 1.15.11: queued agent keys are dropped when HOME closes

Fourth audit, item 14: the overlay takes one key per 12 frames, so keys sent
faster than that (`hbc.py key`, a typed burst) were still in the agent's
queue when HOME closed, and a queued `h` opened HOME again. `home_watched`
now calls the new `agent_key_clear` as soon as the overlay returns, which
covers `hbc_agent_home` and `hbc_agent_home_fb` (HBC's own home.c uses the
latter). No host test: the queue sits behind libogc's ISR macros in the
agent. Checked: channel and `tests/apps/agent_app` build with `-Werror`.

## 1.15.10: a failed tree delete says how far it got

Fourth audit, item 13: a failed op E (an I/O error halfway through a
recursive delete) sent an error with no payload, so `hbc.py` could not say
how much was gone. `file_remove` now sends u32 deleted and u32 total with the
error once deleting has begun; `hbc.py` reports "removed N of M before:
<error>" and does not fall back to entry-by-entry deletes. A success still
sends the 4-byte count and an error before any delete still sends nothing, so
an older `hbc.py` or HBC pairs as before (documented in `docs/devnet.md`).
Checked: new host test with a fake Wii that fails mid-delete; build with
`-Werror`.

## 1.15.9: a listing name cannot leave the folder `get -r` writes into

Fourth audit, item 12: `get -r` is a read-only command, so it may talk to
an auto-found Wii, but `get_tree` joined the names in the Wii's listing onto
a local path unchecked. A hostile or broken Wii could send `..`, `C:\x` or an
absolute path and write outside the target folder. `parse_entry` now refuses
a name that is empty, `.`, `..` or has `/`, `\`, `:` or a NUL, with an
`HBCError` that names it; nothing is skipped silently. Checked: three new
host tests in `tests/host/test_hbc_tool.py`.

## 1.15.8: badge widths on a tiny theme tile are clamped

Third audit, item 11: `badge_gen_bar` computed `tile_w - 2 * BADGE_BAR_INSET`
without a floor, so a theme tile under 16 px gave a negative width. It
now has a floor of 4. `widget_new_badge` stored `w->width - BADGE_INSET -
pill.w` in a `u16`, which wrapped to a huge x on a tile narrower than the
pill; it is now clamped at 0. No host test: widgets.c needs libogc and
the GX types. Checked: build with `-Werror`.

## 1.15.7: a network upload waits for the scan before it is added

Third audit, item 10: the menu loop took an uploaded app's change from
`devnet_take_app_change` and called `app_entry_add` at once, even while the
scan thread was loading the list. `app_entry_add` blocks the UI until the
scan ends and the scan could add the same app a second time. The loop now
leaves the change queued while `app_entry_is_loading()` and takes it on a
frame after the scan. No host test: main.c needs libogc. Checked: build
with `-Werror`.

## 1.15.6: a scan marks every app seen whatever the badge setting

Third audit, item 9: `app_entry_load_single` read `settings.new_badges`
again for every app of a scan. Turning badges off in the Options dialog
mid-scan left the later apps unmarked, and `app_run_end(true)` then pruned
their records. During a scan it now always calls `app_run_status` (which
marks the app seen) and keeps the state only while the setting is on. No
host test: appentry.c needs libogc. Checked: build with `-Werror`.

## 1.15.5: a badge record goes only after two whole scans miss it

Third audit, item 8: libfat's `readdir` shows a read error as the end of
the folder, so a scan that ended early looks whole and `app_run_end(true)`
pruned the records of every app it had not reached. Chosen: prune a record
only after two whole scans in a row missed it. The first miss writes a
` missed` word after the record in apps_seen.txt; a scan that sees the app,
or a launch, clears it; a second miss removes the record. The alternative,
no pruning on an early scan, cannot work because the early scan cannot be
told from a whole one. An older HBC reading a marked line drops it (one
app shows "New" once). Checked: `tests/host/test_apprun.py`, build with
`-Werror`.

## 1.15.4: a table that read as missing is not written over the file

Third audit, item 7: libfat turns a sector read error during path lookup
into ENOENT (its directory.c ignores the result of readPartialSector). One
such fopen of apps_seen.txt made an empty table look readable; the next
app launch wrote a one-line record over the real file and every app showed
"New". `table_write` now refuses when the load saw the file as missing but
`stat()` finds it (or its `.bak`). Checked: `tests/host/test_apprun.py` (a
fopen that lies with ENOENT), build with `-Werror`.

## 1.15.3: an accept() network reset closes the listener

Second audit, item 2: `net_accept` returning -ENETRESET cleaned up the
network and set `s = -1` without closing the listening socket. It now goes
through `tcp_net_deinit("Network reset", &s)`, which closes it inside the
watched cleanup, as the other accept failure already did. (The ENETRESET
from `tcp_listen` has no socket to close.) Checked: build with `-Werror`.

## 1.15.2: a Restart network keeps its watchdog

Second audit, item 1: the TCP worker cleared the recovery request when its
listener came up unless `tcp_restart` was set, a check and a clear with the
menu able to run in between (`loader_tcp_restart` requested, then set the
flag). A Restart asked for in that gap lost its watched cleanup, so a hung
cleanup was never reported. `netrecovery_ready_unless` checks and clears
with interrupts off, and the menu sets the flag before the request.
Checked: `tests/host/test_netrecovery.py`, build with `-Werror`.

## 1.15.0: the crash handler leaves by HBC's own stub and shows more

Review of the exception screen (and the stub it ends in) found:

- The stub's IPC waits had no limit. A request of the crashed app still in
  IOS left its late reply in ARMMSG, IOS then acked nothing more, and the stub
  waited for an ack for good. Now an ack waits 0.5 s, a reply 1 s, a launch
  10 s; a reply that arrives while waiting for an ack is taken; a request
  that timed out gets a fresh `ipc` struct (IOS may still write the old one);
  `reset_ios` stops after three closes with no reply; and the stub ends in
  `ios_last_resort`, a hardware reset where AHBPROT is open and the chip is
  not a vWii, before its final loop. The stub is 5056 bytes (limit 5888):
  `-fno-asynchronous-unwind-tables` drops its unused `.eh_frame`.
- A crash before HBC had installed its stub ended in libogc's `__reload`,
  which calls `SYS_ResetSystem` (IOS and threads, from inside an exception)
  when no stub is there. The handler and `_panic` now install `stub_bin` and
  jump to it; `__reload` and `SYS_ResetSystem` are not called. libogc's weak
  `__SYS_InstallPanicHandler` is overridden, so a crash before `main` (static
  constructors) reaches HBC's screen, not libogc's.
- `HW_RESETS` was written with no AHBPROT or vWii check, and `_panic` waited
  for the reset button for good. Both are gated; `_panic` counts 20 s, shows
  "Reloading in N s", then leaves by the stub; its VI polling loops are
  bounded, and it does not draw when the framebuffer address read from the VI
  is implausible (a VI never set up gave address 0 and wrote over the stub).
- The screen used `__console_init` and `kprintf` (newlib's stream lock,
  `setvbuf`, the heap). It now has its own text and a YUY2 renderer
  (`source/panic.c`, logic in `source/panic_core.h`), redrawn every second.
- HBC's own crash left no `hbc_crash_block`. The handler fills it first
  thing (the agent's layout, app "HBC 1.15.0", reason "thread XXXXXXXX:
  cause"), so `hbc.py crash` shows it after the reload.
- The backtrace starts with `ctx->lr`, then the agent's back-chain walk, with
  a range check on the whole 4 or 8 byte read (MEM1 and MEM2; the thread's
  stack may be in the MEM2 heap, which the first plan did not allow).
- More on screen: HBC version, thread, uptime, DAR and DSISR for DSI and
  Alignment, and a cause decoded from SRR1 and DSISR.
- The audio DMA is stopped first, so a half-dead HBC does not loop a buffer.
- `gfx_deinit` clears `xfb`, so a crash on the exit path (video blanked)
  leaves at once instead of drawing on a blank screen.
- `newrvl.ld` reserved 0x24000 bytes after `.bss` for `__stack_addr` and
  `__intrstack`, which libogc 3 does not use (its stacks are static in
  tuxedo). `__Arena1Lo` now starts at the 32-byte aligned end of `.bss`.
- The countdown no longer goes negative if the reload returns: the handler
  does not return, it ends in a hardware reset or a spin.

Checked: `tests/host/test_panic_host.py` (range check, walk, cause text, crash
block validity, the IPC wait truth table and its end across a time base
wrap), `tests/host/test_memory_layout.py` (arena start, early handler),
`tests/host/stub_layout.sh`, build with `-Werror`.

- A crash on every start reloaded for good: the stub starts the installed
  channel, which crashed again (before 1.15.0 such a crash reset the Wii).
  When HBC crashes within 30 s of its start and the record before it (the
  MEM2 block, or the copy `devnet_early_init` took) is HBC's own crash within
  30 s of its start, the stub is pointed at the System Menu instead
  (`panic_crash_loop`). Where Priiloader autoboots an HBC, the loop goes on
  through Priiloader until RESET is held at power-on: HBC cannot change that.
- The cause text called DSISR bit 5 "lwarx/stwcx to write-through". On the
  750 it is a direct-store segment, and a real Wii's segment registers make
  every address below 0x80000000 one: a store to address 0xA gave DSISR
  06000000 on the bench Wii. It now reads "direct-store segment (bad
  address)".

Checked: `tests/host/test_panic_host.py` (range check, walk, cause text, crash
block validity, the crash-loop rule, the IPC wait truth table and its end
across a time base wrap), `tests/host/test_memory_layout.py` (arena start, early
handler), build with `-Werror`, host suite 321 tests. Dolphin: the agent
crash, fatal, hang and exit checks on the 1.15.0 WAD; a crash-1 WAD built as
LULZ starts twice, then the stub launches 00000001/00000002 (Dolphin's NAND
has no Wii Menu to show).

On the dev Wii (2026-11-05): crash-1 (a fault before the video is up) went
back to the installed 1.14.0 at once and `hbc.py crash` showed "HBC 1.15.0
crashed after 0.0 s: DSI", DAR 0000000a (job 20261105-002047-cf301a);
