# HBC 1.14.x: findings and hardware results

What each 1.14.x change found, fixed and measured, newest first. The short list of
changes is in [CHANGELOG.md](../../CHANGELOG.md); open items are in
[review.md](../review.md).

## 1.14.31: a network hang leaves HBC running; reloading is a developer setting

PR 22 reloaded the whole channel when a network cleanup hung inside IOS,
after a 10 s countdown on an error dialog. Monty found that too brutal for
everyone's Wii: a network that hangs on every start would reload HBC again
and again. Restarting only the network is not possible with libogc 3.1: its
`net_init_async` keeps a private busy flag that only an IOS reply clears,
and an IOS reload does not clear it, so only a fresh HBC can start the
network again. Now a hung cleanup leaves the menu and app launches running
(an app gets a fresh IOS anyway), and a timed information message says the
network comes back the next time HBC starts. `hbc.py net-hang reload`
(HBCR, `settings.xml` `net_hang_reload`, no menu row) brings back the
immediate reload, without the countdown, for a developer's Wii that must
stay reachable. An exit or launch now parks the TCP worker whenever it could
not be stopped, not only before a recovery reload.

Also from the 1.14 audit of PR 22: Restart network and an accept failure
close the listener inside the cleanup watchdog (`net_close` waits on IOS
too); a start that runs out its 30 s on netinit_wait's own timeout gets the
30 s cleanup wait, like a cancelled one; the retry timer is reset once the
network is up; `test_netrecovery.py` honours `CC`.

- **Checked:** in Dolphin with `HBC_TEST_STUCK_NET_CLEANUP`,
  `tests/dolphin_network_recovery.py` (default) keeps HBC running 40 s after
  the wedged Restart with no IOS reload and no relaunch; with `--reload` the
  channel is relaunched once through a fresh IOS 8 s after the press, and
  does not loop. `NetHangTest` checks the HBCR bytes; host suite passes.
- **On the bench Wii (1.14.27 plus this change):** Restart network
  (`C:/Temp/hbcpr/restart_wii.py`, job 20261104-214236-fbfc34) counted one
  more network start within 0.5 s of the press, and HBC never missed a
  status poll every 0.2 s. So Restart closes and reopens HBC's network
  handle and listener, while IOS keeps its Wi-Fi link and address: it does
  not join the network again, which is why the icon lights at once (and why
  the 1.14.21 check saw "back after 0.0 s").
- **Idea, not done:** a true in-place restart would need HBC's own copy of
  libogc's network start (to own the busy flag) and an IOS reload with SD,
  USB and the remotes closed around it.

## 1.14.28: sdk/slotled, the disc-slot light; the WiiConnect24 SDK's plan

`sdk/slotled` drives the blue slot light every way the Wii allows:
- **Directly:** the PowerPC's GPIO bank, pin 5. 256 levels by modulation
  from two alarms, with no thread, and nothing running when the level is
  steady. Effects: blink, pulse, heartbeat, Morse code, steps of your own,
  and a flash over what runs.
- **Through IOS:** `/dev/stm/immediate`: the off/dim/bright level (0x6002),
  the 30 built-in flash patterns (0x6001), and the raw ioctl for its flags.
- **The saved setting:** the Wii Menu's Slot illumination, the last byte of
  SYSCONF's `IPL.IDL`, written in place.
  - **Its size:** libogc and Dolphin make `IPL.IDL` 2 bytes, while WiiBrew
    says 3. The patcher takes either, and `slotled_app check` prints the
    bench Wii's.

The WiiConnect24 SDK's plan is [docs/plans/wc24.md](../plans/wc24.md):
`sdk/wc24` goes under `sdk/mboard`, with WiiLink as the first service and
Wiimmfi as a separate WFC part.

- **Checked:** `tests/test_slotled.py` (15 tests: duty, builders, the step
  engine, the SYSCONF patcher). `tests/dolphin_slotled.py` passes: the
  timer, `slotled_wait` exact at 600 ms, the pin left as it was found.
- **Not yet:**
  - `tests/wii_slotled.py check` on the dev Wii: it is queued, but the
    bench's lease server was unreachable.
  - `demo` and `ios` need someone watching the light.
  - `save` writes SYSCONF: only on request.

Future SDK ideas, each waiting for someone to want it:
- **MotionPlus orientation.**
  - Has: libogc gives the raw gyro rates.
  - Missing: fusing them with the accelerometer into a steady direction
    that needs no sensor bar.
  - Pure maths, so it can be tested on a PC.
- **Wii Remote pairing and system settings.**
  - Has: libogc already has `CONF_Get/SetPadDevices` and
    `WPAD_SetHostSyncButtonCallback`.
  - Missing: a safe layer to list, add and remove pairings, with a backup
    of SYSCONF.
- **Titles, banners, free space.**
  - Has: `ES_GetStoredTMD` and `ISFS_GetUsage` exist.
  - Missing: banner and icon reading, which today lives inside USB Loader
    GX and WiiFlow, not in a library.
- **Wii Speak and USB microphones.**
  - Has: no libogc driver. WiiBrew documents the Wii Speak's start-up:
    vendor commands and a firmware upload.
  - A standard USB microphone is simpler.
- **Save data export and import.**
  - Needs the SD key, which must come from the user's own files, never
    from the repository.

## 1.14.26: app badge records are read whole or not written

From the 1.14 audit, three gaps in PR 17's `apprun.c`:
- **No lock.** The scan thread holds the table from `app_run_begin` to
  `app_run_end`, while the menu's `app_entry_add` (an app sent from the PC)
  and the loader's `app_run_record` loaded and freed the same static table,
  and `badge_scan` was a global the menu read as "a scan is open". A lock in
  `apprun.c` now spans a scan and each one-off call, and `in_scan` is passed
  to `app_entry_load_single` instead of read from a global.
- **A failed read was an empty table.** An open error other than ENOENT,
  or a read error, left a partial table that `app_run_record` then wrote
  back with one app in it, and a whole scan pruned from. Now nothing is
  written or pruned after such a read, and a `readdir` error (errno, not
  just a NULL) makes the scan incomplete.
- **Names and failed snapshots.** Folder names compare without case, as FAT
  does. A folder that cannot be stamped (no boot file, a stat error) now
  shows no badge rather than Updated, which no launch could ever clear.

- **Checked:** `tests/test_apprun.py` (16 tests; new: an unreadable file is
  never rewritten or pruned, names ignore case, an unstampable folder is not
  Updated). `tests/dolphin_app_badges.py` passes with the 1.14.26 retail WAD.
- **Not covered:** the race itself (a transfer that lands during a device
  scan) on the bench Wii. `entries_all` has the same race between the scan
  thread and `app_entry_add`, older than the badges; it is left for its own
  change.

## 1.14.25: HBCU answers only queries

From the 1.14 audit. `discover_poll` answered any datagram that began with
`HBCU`, replies included, so two consoles on one network (or one whose
reply came back to it) could keep answering each other. It now answers only
a 16-byte query with byte 4 zero (a reply's version is 1), and nothing sent
from port 4299, where every console replies from (`discover_is_query` in
`discover.h`, shared with the agent).

- **Checked:** `tests/test_discover.py`. On the bench Wii (1.14.25): a query
  is answered and `hbc.py find` lists it; the same query from port 4299, a
  12-byte query and a reply-shaped one get no answer.
- **Held:** the audit's network fixes 14, 15, 16 and 18 touch PR 22's code,
  which Monty wants to rethink first (the recovery and its dialog). They are
  written and pass in Dolphin, but are kept out of the tree as a patch in
  the session notes (`pr22-audit-fixes-14-15-16-18.patch`).

## 1.14.24: no rm -r pattern in an apps folder; hbc.py log never guesses

From the 1.14 audit. 1.14.16 refused `rm -r` with a wildcard at a device's
top, but only in `hbc.py` and only when the folder ended in `:`, so
`rm -r sd:/apps/*` deleted every app, and `sd://*` passed the check. Now
`hbc.py` refuses a recursive pattern whose folder is a device root or its
apps folder however spelled (`protected()`, the same parse as the rest of
the deletes: `SD:/./Apps`, `sd://apps`), and so does the Wii:
`file_remove` replies EPERM before it reads anything
(`devfile_glob_refused` in `devfile_rm.h`), for clients other than hbc.py.
A pattern one level down (`sd:/apps/myapp/*`) still works. Also: `log`
left `hbc.READ_ONLY`, because it points the Wii's log at this PC, so with
no address it no longer uses whichever Wii answers; and `--wii=` with
nothing after it is an error rather than "find one". The audit saw the
no-address error without the Wii that answered; the bench log of
1.14.21's run (`20261102-192049-ca7496`) shows it there, so that is left.

- **Checked:** `tests/test_hbc_tool.py` (rm -r in apps, five spellings,
  refused before any request; the fake Wii's EPERM; `log` and an empty
  `--wii`), `tests/test_devfile_rm.py` (`devfile_glob_refused`). On the
  bench Wii (1.14.24): `rm -r sd:/apps/zzrmtest*` sent straight to the Wii
  came back EPERM with both scratch folders still there, and
  `sd:/apps/zzrmtest1/*` deleted its two files.

## 1.14.23: the USB keyboard in HOME, rollover, and devices it skipped

From the 1.14 audit. Esc or Home on a USB keyboard opened HOME, but the
overlay reads only remotes and GameCube controllers, so the keyboard could
not move in it or close it; and the keys pressed there waited in
`keyboard.c` until HBC's loop came back, where an Enter launched the
selected app. HBC's `on_frame` callback now scans the keyboard each overlay
frame and passes its keys to the agent's key queue through a new
`hbc_agent_push_keys` (the queue `hbc.py key` fills), so the keys are used
up there; one scan after the overlay closes keeps a key still held from
reading as a new press. Also in `keyboard.c`: a rollover report (too many
keys, every slot 1) kept nothing, so every held key went up and came down
again as a new press when it ended; it now keeps the last keys. A device ID
was marked seen before it was opened, so a keyboard whose open failed once
was never tried again, and IDs of unplugged devices filled the list; now
only devices proven not to be keyboards are remembered, and only while they
are plugged in. A read IOS never gave back after `keyboard_shutdown` would
write into, and call back into, the app on the `no_ios_reload` path: HBC then
reloads the same IOS, keeping AHBPROT, before the launch.

- **Checked:** `tests/test_keyboard.py` builds `keyboard.c` against a fake
  USB (`tests/keyboard_host`): rollover, a retried open, a mouse opened once,
  a forgotten ID, a pending read after shutdown. Five of its ten checks fail
  on 1.14.22's `keyboard.c`. The DOL builds with `-Werror`.
- **Checked on the bench Wii** (attended, `C:/Temp/hbcpr/kbd23_wii.py`,
  job 20261102-213308-4d0049): with only a USB keyboard, Esc opened HOME,
  the arrows moved its focus, Esc closed it; Esc, HBC, Enter, About, Enter
  opened About. Afterwards 1.14.23 still answered and no app was running.
- **Not yet checked:** the `no_ios_reload` reload needs a read IOS never
  answers, which the bench cannot make happen on demand.

## 1.14.22: the crash screen from the first instruction, and once only

The 1.14 audit found two gaps in 1.14.3's `hbc_exception_screen`. It was
installed at the end of `gfx_init_video`, so a fault before that (devnet,
`zmem_init`, audio) still went to libogc's screen and its XFB over HBC's
stacks. And a fault inside the screen came back into it, on the same
stack, with no end. `main` now installs it before calling anything else; with
no framebuffer yet it reloads at once, and a second entry resets the Wii
the way `_panic` does. `HBC_TEST_CRASH=1|2|3` builds fault before the video,
8 s into the menu, or also inside the screen.

- **Checked:** `tests/test_memory_layout.py` fails unless
  `panic_install_exception_screen` is `main`'s first call. On the bench Wii,
  the crash-1 build reloads the installed channel (1.14.0 answered); the
  crash-2 build shows the DSI dump (DAR 0000000A) and the countdown on the
  capture card, then reloads.
- **Checked, attended:** the crash-3 build (a fault in the screen) reset
  the Wii by itself about 20 s after the send: the capture card shows
  BootMii's menu, then the installed 1.14.0, which answered (job
  20261102-213605-858fed).
- **Left:** audit items 3 (stack walk floor) and 4 (the unused 144 KiB
  `__stack_addr` reservation in `newrvl.ld`) are not done.

## 1.14.21: HBCU discovery answers on a real Wii

PR 21's discovery passed in Dolphin but no Wii ever answered `hbc.py find`.
A diagnostic build counted the queries arriving (16 bytes, from the PC) and
`net_sendto` failing with -22: the reply passed `sizeof(from)` (16) as the
address length, and libogc hands that to IOS as `sa_len`, which on a real
Wii takes the 8-byte address `recvfrom` filled in (`fromlen` came back 8).
Dolphin accepts 16. The reply now passes `fromlen`.

- **Checked:** on the bench Wii, `hbc.py find` lists it, `hbc.py version`
  with no address finds it, and `put` with no address refuses.

## 1.14.19 and 1.14.20: PR 22, network starts and cleanups that IOS never finishes

Matt's PR bounds a network start at 30 s (`netinit_wait`, restart and exit
seen every 50 ms), cleans up through one helper (`tcp_net_deinit`) that the
menu watches (`netrecovery.c`), and, if a cleanup has not returned after
5 s, shows a countdown, reloads IOS and starts the installed channel through
its stub. 1.14.19 is the merge. Both PRs edited the `net_deinit` call sites
in `loader.c`; `tcp_net_deinit()` now calls PR 21's `discover_stop()` itself,
inside the watchdog (`net_close` waits on IOS too), so restart, ENETRESET,
listener and accept failure, a failed start and thread exit all stop
discovery.

**With 1.13.15's retry (`net_failed_at`, `net_retry_ms`):** PR 22 bounds one
start at 30 s and cleans up after it; the retry schedules the next start
(2 s, 4 s ... 32 s) once the worker is back in `UNINITIALIZED` with its
command idle. A cleanup that returns never reloads the channel, however long
the network stays down; only a cleanup stuck in IOS does. A restart resets
the backoff as before.

1.14.20, from the review:
- A restart cancels a start between IOS steps, and `net_deinit()` then waits
  for the step in flight, which can take most of the start's 30 s. The 5 s
  cleanup watchdog would reload HBC for a slow IOS. After a cancelled start
  (`start_cancelled`) the cleanup gets 30 s
  (`netrecovery_cleanup_begin_after_start`); every other cleanup keeps 5 s.
  libogc's `_init_busy` is private, so the worker's own flag is used.
- The "Reinit" block (`state == INITIALIZED` with `cmd INIT`) is gone. Every
  setter of `LDTCPCMD_INIT` has `UNINITIALIZED` as the state (the thread's
  start, restart, ENETRESET in listen and accept, `loader_tcp_init`, and the
  retry), so it could not run once the merge made those paths set it.
- `SO_REUSEADDR` in `tcp_listen` stays. `tcp.c` is shared, so it also
  reaches the agent's listener (`sdk/hbc_agent`): a listener reopened at
  once after an app exits or the network restarts can now bind with old
  connections in TIME_WAIT. No harm seen; it is not tried on a Wii.
- `tests/test_netrecovery.py` covers the 30 s case.

**Open risk:** the recovery (IOS reload, then the channel through its stub)
has only been run with a simulated hang (`HBC_TEST_STUCK_NET_CLEANUP`, in
`tests/dolphin_network_recovery.py`), not with a real stuck IOS request. If
IOS is truly wedged, `__IOS_LaunchNewIOS` may hang too, which is worse than
before: HBC would sit on a frozen screen instead of an unresponsive network.
A power cycle is then the only way out. `tests/test_netinit.py` needs a
POSIX compiler (it does not build with clang or MSYS gcc on this PC).

## 1.14.17 and 1.14.18: PR 21, find Wiis with a UDP query (HBCU)

Matt's `HBCU` query (port 4299, `docs/devnet.md`): HBC, and an app with the
agent, answer a broadcast with the console's address and a name, and
`hbc.py find` lists what answers. 1.14.17 is the merge, unchanged.

1.14.18, from the review:
- With no address set, every command ran a find and used the one Wii that
  answered, so `send`, `rm`, `put`, `sync` or `mv` could land on a Dolphin
  or on someone else's Wii. Now only `status`, `version`, `hw`, `ls`, `stat`,
  `get`, `log`, `find` and `wait` auto-find (`hbc.READ_ONLY`). The others
  fail as before, and the message shows the address that answered to pass
  with `--wii`. `wii_address(arg, auto_find=False)`: the test scripts that
  call it directly keep failing as before.
- `find --timeout=0.5` was ignored (find looked for the word `--timeout` in
  argv). The default is a sentinel now and either form, before or after the
  command, counts; `split_flags` takes `--flag=value`.
- Tests: `FindGuardTest` in `tests/test_hbc_tool.py`.

**What it reveals on the LAN:** the Wii's IP and name, to a PC in the same
/16. HBCS over TCP already gives the same to anyone who connects, so a
reply tells no more than a connect does.
**Left as they are:** a reply is sent for at most 8 queries per poll frame,
so a flood is bounded; the broadcast has not been tried on a real Wii yet
(Dolphin and the unit tests only), so whether a console's own IOS delivers a
broadcast on 4299 is unproven. The first test on the bench is
`hbc.py find`.

## 1.14.15 and 1.14.16: PR 20, deletes of trees and patterns in one request

Matt's op `E` (protocol 9, `docs/devnet.md`) deletes a tree or a pattern's
matches on the Wii, with "Deleting" and progress on screen; `hbc.py rm` and
`sync --delete` use it and fall back to one request per entry on an older
HBC. Paths are checked by `valid_path` as before, and HBC itself refuses a
device root or `<device>:/apps`.

1.14.16, from the review:
- `hbc.py rm -r` takes no wildcard at a device's top: `sd:/b*` took
  `bootmii/`, `usb:/*` a drive with no `apps/`. One level down works.
- The network thread's stack is 12 KB (was 8): on the bench Wii a 16-level
  tree (the most op `E` allows) used 6344 bytes of 8192; a 40-file pattern
  and the tree each went in one request.
- "Deleting" is in `template.pot`.

**Left as they are:** each delete rescans its folder from the start, so a
folder of thousands of files is slow; nothing notices the PC leaving
mid-delete (an app launch still stops it); without `-r` the Wii deletes a
matching empty folder where the older-HBC fallback refuses; `?` is one byte
on the Wii and one character in the fallback.

## 1.14.14: PR 17, app badges keep their record in one file per device

Matt Sephton's PR 17 (1.14.13) kept an `.hbc-ran` file in every app folder.
Monty chose per-device files on the card instead, to keep NAND writes down
(there are none) and the app folders clean: `<device>:/hbc/apps_seen.txt`,
one line per app (folder name, then the size and modified time of
`boot.dol`, `boot.elf`, `meta.xml` and `icon.png`). A scan reads it once
and, if apps have gone, writes it once; a launch writes it. The write is a
temp file and a rename, keeping the PR's handling of libfat refusing to
replace an existing file. A read-only or failing card just forgets: badges
do not persist. The never-shipped "version 1" marker migration is gone.
The look changed to a solid "New" or "Updated" pill in the tile's top-right
corner (Updated also gets a 3 px bar along the top edge), coloured by the
theme keys `badge_new` and `badge_updated` (`<fill>` and `<text>`). Only the
app list's own launch records a run; Wiiload, USBGecko and HBCA uploads do
not.

- **Options layout:** with the PR's fourth setting row, 0.7 scale and the old
  spacing do not fit the 360 px dialog: the last row would end at 332 px,
  past the Ok buttons at 306. The PR's 0.6 scale and tighter spacing (last
  row ends at 302) are kept; the captions' font is not scaled.
- **Checked:** `tests/test_apprun.py` on the host; the DOL builds with
  `-Werror`; Dolphin smoke and badge runs (see the commit).
- **Not yet checked:** a real Wii: that a USB drive's file is kept apart
  from the SD card's, and a locked SD card.

**Trigger:** switch App badges on with a few apps on the bench Wii's SD
card and a USB drive; launch one and come back.

1.14.8: on the bench Wii the keyboard did nothing. HBC starts libogc's USB

## 1.14.3: the crash screen shows its text again

A crash in HBC itself showed no text, and on the bench Wii (a Balance Board
syncing with 1.14.0) it then went to standby and ignored the buttons.
libogc 3.1.0's crash screen (`default_panic.c:50`) clears a fixed XFB at
0x81700000, "above ArenaHi" for a normal app. HBC's `.bss` runs to
0x81753900 (ArenaHi 0x817FEFF0, `newrvl.ld`), so the clear wiped HBC's
stacks, among them the exception stack the handler runs on, and it went off
the rails before printing. `panic.c` now installs `hbc_exception_screen` as
`PPCExcptCurPanicFn`: the same dump on the framebuffer HBC already shows,
then RESET, Z on a GameCube Controller, or 20 seconds reloads. It points the
VI at that framebuffer with `VIDEO_SetFramebuffer`, which writes the
registers at once: `VIDEO_SetNextFramebuffer` and `VIDEO_SetBlack` wait for
a retrace interrupt, and an exception has none (the first bench try showed
no picture). The countdown rewrites one line, so the dump stays on screen.

- **Checked:** on the bench Wii, a scratch build that writes to address 10
  eight seconds into the menu shows "Exception (DSI) occurred!", the
  registers and the stack on the capture card, counts down, and reloads the
  installed channel (it answers 1.14.0). In Dolphin (MMU on) the same, read
  from the XFB over the GDB stub. `tests/test_memory_layout.py` fails if HBC
  ends past 0x81700000 without its own screen.
- **Not covered:** a crash before `gfx_init` has unblanked the screen stays
  black (the VI is still black then), though it still reloads. Without a
  stub (`STUBHAXX`), Dolphin spins in `SYS_ResetSystem`'s reset callbacks;
  that path is libogc's own.

## 1.14.1: a fourth Wii Remote, or a Balance Board, no longer crashes the channel

libogc 3.1's `wiiuse_init` builds each of its six Bluetooth slots a queue of
256 commands in the kernel heap, 64 KB shared with its threads. Three fit;
slots 3 to 5 keep an empty queue, and the first command to a device there
(its LEDs, as it connects) reads address 0. `source/wpadqueue.c` builds the
queues from the normal heap instead, through `-Wl,--wrap=wiiuse_init_cmd_queue`
on the app's link (not the stub's).

The wrap is needed: `wiiuse_init_cmd_queue` is defined in libwiiuse's
`io_wii.o`, with `wiiuse_io_write` and `wiiuse_accept` that the rest of the
library uses, so defining our own would collide; `wiiuse_init` calls it from
inside libwiiuse, and `__wpads` is static, so nothing public reaches the
queues. Only this one function is wrapped.

- **Checked:** `tests/dolphin_wpad_queue.py --stock` boots
  `tests/wpad_queue_app` on libogc as it is and reads the six queues: slots 0
  to 2 built, 3 to 5 not. The same app with `wpadqueue.c` has all six. The
  channel DOL builds with `-Werror`, and `tests/dolphin_smoke.py` boots it.
- **Not yet checked:** a fourth Wii Remote or a Balance Board connecting to
  the channel on a real Wii; Dolphin cannot connect either.

**Trigger:** pair four Wii Remotes (or a Balance Board) with the bench Wii
and connect them in HBC; before this change the program crashes.

1.14.2: the wrap returns `void`, as libogc's function does, and if neither
heap has room the slot gets an empty queue, so commands to it are dropped
(`wiiuse_sendcmd` already checks for none) instead of read from address 0.
Seen on the bench Wii: 1.14.0 crashes as a Balance Board syncs; 1.14.3 kept
answering `hbc.py` through a 90 s Balance Board sync.
